Summaries of each `.ts` file under `ts/src/v2/`, roughly following the compilation pipeline: **parse → expand → fixpoint eval (store) → render**. The first four files (`term.ts`, `hashcons.ts`, `unify.ts`, `aggregators.ts`) are the core term layer, duplicated from v1 so v2 is free-standing (see `plans/v1-cleanup.md`); the deprecated v1 originals live under `ts/src/v1/`.

# term.ts

The core term layer: the `Term`/`Atom` data types shared by every phase, source `Span`s, the `NodeId` token key space, and the substitution `Trail` (two parallel mutable arrays; bind = push, backtrack = truncate). Duplicated from the v1 `types.ts`, minus the v1-only `Tree`/`Constraint`/`TurnExpr` IRs.

**Key terms:**
- `Term` — the term algebra: `Symbol` | `Variable` | `Atom` | `Id` | `Wildcard` | `Ref`
- `Atom` / `Span` — a term list; a source position: 1-indexed line plus 0-indexed `startCol`/`endCol` covering one atom's text (marker included)
- `spanKey` — `"line:startCol-endCol"` DOM key for `data-source-span` linking; `undefined` for a column-less span
- `NodeId` — integer key space for hashconsed terms (disjoint ranges per tag)
- `Trail` — substitution trail: `newTrail`/`trailPush`/`trailLength`/`trailUnwind`/`trailLookup`
- constructors — `sym`, `vari`, `ref`, `atom`, `idTerm`, `isId`

# hashcons.ts

The hashcons engine (duplicated from v1): a trie keyed by `NodeId` tokens interns `Atom`/`Id` bodies to integer-`Ref` terms, with disjoint sub-tries per tag so structurally identical `Atom` and `Id` bodies never collide. `store.ts` owns one `HashconsState` per `Store`.

**Key terms:**
- `HashconsState` / `createHashcons` — the trie + ref/sym/var id tables; factory reserves the `*atom*`/`*id*` sentinel tag tokens
- `hashconsTerm` / `hashconsAtom` — intern a term (bottom-up) to a `Ref`; map an atom's terms
- `tokenOfId` — `Term` → integer token (Ref +N, Wildcard 0, Symbol odd-negative, Variable even-negative)
- `refTagOf` — whether a Ref's stored body was an `Atom` or an `Id`
- `expandTerm` — inverse: unfold a `Ref` back to a structural term

# unify.ts

Trail-based term unification and substitution (the v1 `unify.ts` trimmed to its term layer — the TurnExpr/RefStore-driven `unifyConstraints`/`unifyTree` machinery stays in v1). Primitives never unwind the trail on failure; choice-point callers mark/unwind. Variables are never bound to raw atoms: bindings are substituted, groundness-checked, and hashconsed to `Ref`s first.

**Key terms:**
- `resolveVar` — chase variable bindings to the first non-Variable term (no descent into atoms)
- `substTerm` / `substAtom` — full recursive substitution for materializing concrete terms
- `unifyTerms` / `unifyAtoms` — structural unification over the trail; `Atom` vs `Id` never unify; `Ref`s unify by token or by stored body against a structural term
- `unifyStats` / `resetUnifyStats` — cheap call counter used by perf experiments

# aggregators.ts

The aggregator registry (duplicated from v1): named fold definitions. With `#agg`/`#reactive` and bracket aggregation removed (plans/v2-caret-fresh-left.md §5.4), its remaining users are acc-ops.ts (the `count` fold behind `@count`) and the parser. Each aggregator is a `zero` term plus a binary `fold`, with a commutativity flag.

**Key terms:**
- `Aggregator` — `{ zero, fold, commutative }`
- `aggregators` / `getAggregator` — the registry (`count`, `sum`, `last`, `bool`) and its throwing lookup

# types.ts

Defines the v2 intermediate representation (IR): the `RuleAtom` algebra spanning both pre-expand (parser output) and post-expand (evaluator input) phases, the `Rule`/`Program` containers, stored `Tuple`s, and the result types for a fixpoint run including blocked-choice reporting. It documents the compilation pipeline (parse → expand → fixpoint eval → Store) and how source markers desugar into explicit anchor IR.

**Key terms:**
- `RuleAtom` — the core tagged-union IR node: pre-expand (`Atom`, `Sub`, `Exception`), both-phase (`Equal`), post-expand (`Match`, `Emit`, `Le`, `AssertLt`, `JsIterate`), and the acc-rule-only `AccMatch` / `AccContribute` (a read of a local acc row while a moment's rows are being computed; the head of an acc rule as one contribution — plans/v2-acc-relations.md)
- `Expr` — the rhs of an `Equal`: a plain `Term` (unified structurally) or, post-expand only, a computed `Max` / `Min` (moment-order larger / smaller; incomparable args fail relationally) or `JsCall` (a user `#js` function) whose result unifies with the lhs. `isTermExpr` / `exprTerms` / `mapExpr` are the walking helpers
- `Atom.after` — set by `>p` / `~>p`; the rule continues after `p` ends (see expand.ts)
- `Atom.negated` / `SubConstrain.negated` / `Match.negated` / `AccMatch.negated` — a `not r t̄` read of an `#acc` relation: succeeds, binding nothing, iff no row matches at the read's moment (plans/v2-caret-fresh-left.md §3)
- `Atom.exact` / `Atom.exnCheck` — compiler-internal flags set only by `applyExceptions`: an `anchor` emit that lands exactly on the running anchor (no fresh left end), and the default rule's handler-answered "no flag alive at the anchor's start" check (plans/v2-caret-fresh-left.md §5.2)
- `Marker` — pre-expand source marker (`match`/`episode`/`fact`/`anchor`/`ask`/`constrain`) driving desugaring
- `MatchConstraint` — semi-naive eval tag (`"any" | "delta" | "old"`) on `Match` atoms
- `Rule` / `Program` — named rule (body + delta fields) and the top-level container (`rules`, `jsDefs`, `jsRels`, `accDecls`, `accRules`, `provLinks?`)
- `AccColumn` / `AccDecl` / `AccRule` — one column of an `#acc` declaration (a key column with a documentary type, or the single agg column naming a registry op); the declaration (`columns`, `aggIndex` — null for a boolean relation); an acc rule `body / head` (pre-expand body of matches and `=`, head atom with the agg column already unwrapped to the bare contribution term). See acc-ops.ts / acc.ts
- `Tuple` — stored datum: `atom` plus interval endpoints `l`/`r`
- `JsDef` / `JsRelDef` — user-defined `#js` function; one `#js-def` js-relation clause (mode-marked params + generator body, plans/v2-js-relations.md). `RuleAtom` gains the post-expand `JsIterate` variant: a js-relation match lowered to a generator enumeration (arg terms only — no head, no trailing id slot, no anchor effect), with `defIndex` naming the clause picked by `resolveJsModes`
- `FixpointStatus` — run outcome (`done`/`gas`/`active-choices`/`empty-fringe-error`)
- `Actor` / `ACTOR_PRIORITY` / `maxActor` / `isActor` — the finite choice-actor set (`you` > `rng`, plans/v2-choice-actors.md); `you` is the human default, `rng` resolves uniformly at random in the scheduler
- `ComponentOptions` / `BlockedChoose` — per-component choice enumeration (with a per-active-term `actors` array); a blocked choose row (with its ask atom's `actor`)

# parse.ts

The v2 parser for the flat-syntax language: it tokenizes input line-by-line (comment- and indentation-aware) then turns the token stream into a `Program` (rules + acc declarations), without applying hashconsing. Rule boundaries follow the offside rule: a line whose first character is at column 0 starts a new definition, indented lines continue the enclosing one, and blank lines carry no meaning (inside an open `(`-group the boundary is ignored, so a multi-line sub may return to column 0). It handles markers, `=` equality, `#def`/`#acc` commands, `not` reads, parenthesized/sequence sub-rules, dot-notation desugaring, `!(...)` compound constrain blocks, and acc rules `body / head`. The removed aggregation forms — `#agg`, `#reactive`, `-> weight`, bracket aggregation `[ … ]` and `#macro` — are still recognized, only to report a migration error (`REMOVED_AGG`) pointing at `#acc`.

**Key terms:**
- `parse` — top-level entry (tokenize → `parseProgram`); returns a `Program` or a `ParseError` (`{ line, message }`)
- marker chars — `-~+^!?` map to a `Marker`
- `>p` / `~>p` ("after") — a `>` right after the marker (or as the first char of an unmarked atom) sets `Atom.after`. Only a plain match or an episode may carry it; a fact, `^`, `?`, `!`, an exception LHS, and acc rule bodies and heads are rejected. `;` sequencing is unchanged
- dot-notation desugaring — threads fresh anchor vars across atoms/subs. A lone variable on the left of a dot (`A.p X`, a bare `match` atom whose only term is a Variable — `loneVariable`) is the value to thread rather than an atom to match: the placeholder atom is dropped and `A` takes the place of the fresh var, so the right side reads `p A X` under any marker (plans/v2-dot-notation.md, addendum)
- arity saturation — `saturateArity` pads each Symbol-headed atom with trailing wildcards up to its lexical arity (`:`-count + 1), run after dot-desugaring; over-arity atoms are left as-is (plans/v2-arity-auto-wildcard.md)
- ask atoms `?[actor] V1 .. Vn` — an optional `[actor]` group glued directly after the `?` marker (tokenizer consumes it into the atom text; a spaced `[` is the removed bracket aggregation, a migration error) selects the resolving actor (`you` default, `rng` random — plans/v2-choice-actors.md); the ask shape is validated to one-or-more distinct Variables (no symbols/compounds/`_`/duplicates)
- `!(...)` constrain blocks — parsed into compound `subAtoms`
- `not r t̄` — `splitNot` strips a leading reserved `not` from a plain atom (or a `!(...)` sub-atom) and sets `negated`; `not` with a marker, or `not` not followed by a relation name, is an error, so the word never names a relation. That the relation is an `#acc` one, and that the read is range-restricted, is checked in expand.ts
- removed aggregation (`REMOVED_AGG`) — `#agg`/`#reactive` commands, a top-level `->` in any atom, `!(...)` sub-atom, `=` or exception LHS, an `aggcomp` (`[ … ]`) token and a `macroDef` (`#macro … :=`) token each fail with one migration message; the tokenizer still produces the last two so the error can name them
- `{p t1..tn => e}` exception blocks — tokenized on `{`/`}`, split on top-level `=>`; LHS a single unmarked Symbol-headed atom, RHS a body fragment (no nested exception, no dot adjacency; may be empty = bare suppression); becomes a pre-expand `Exception` atom (plans/v2-exceptions.md)
- `#def` commands — rule naming
- `#acc name : col…` and `body / head` rules (plans/v2-acc-relations.md) — `parseAccDeclText` reads the columns (a Symbol is a key column's type; a bare `@op` or a group `(@op base)` is the one allowed agg column, validated against the acc-ops.ts registry; the `:` must be a standalone token). A standalone `/` (whitespace on both sides — `do/rest` stays a Symbol) tokenizes to a `slash` token, which `parseBodyItems` stops at (an error inside a group or an exception block); `parseProgram` then parses the head as a second body and `buildAccRule` assembles the `AccRule` — body restricted to matches and `=` after dot-desugaring, head exactly one unmarked, un-negated atom. `validateAccRule` runs after the loop (declaration order is free): head declared and of the declared arity, the agg column unwrapped from `(@op T)` / `()` to the contribution (checked against the op's `arity`). `#acc` names are disjoint from js and js-def names; auto-naming shares one counter with ordinary rules
- `#js-def name ±p1 .. ±pn { body }` — one js-relation clause (plans/v2-js-relations.md): unparenthesized signature with `+` (bound) / `-` (enumerated) mode marks, generator body collected with the `#js` one-liner/multi-line rules. Clauses accumulate per name in `Program.jsRels` (declaration order = selection priority); parse enforces same arity across a name's clauses, distinct mode vectors, and that js-relation names are disjoint from `#js` functions and `#acc` declarations — a js relation claims its name exclusively, since match sites never read the store

# expand.ts

The expansion pipeline that lowers parsed pre-expand rules into the flat post-expand IR: it runs anchor decomposition (`decomposeRule` + `pruneChains`), universal rule-splitting on every `Emit`, dead-slice filtering, and semi-naive delta-variant generation. The core anchor-decomposition pass threads SSA running-anchor variables and a `*chain` fingerprint, lowering each marker (match/episode/fact/anchor/ask/constrain) into the right combination of `Match`/`Emit`/`Le`/`AssertLt`/`Equal` (with `max`/`min` rhs for the window step). `max`/`min` appear only at matches (the anchor intersection with a stored tuple's endpoints); emit and sequence-sub anchor updates are statically determined by the running-anchor invariant and emit no atoms.

**Key terms:**
- point windows fail — `decomposeMatch`'s overlap checks are strict (`Le.strict`): `XL < r`, `l < XR` and `l < r`, so a match whose intersection `[max(XL, l), min(XR, r)]` would be a single moment fails like a unification failure (it used to pass, and a `~` emitted into the point needed `XL < l' < r' < XR` with `XL = XR`, a cycle in the moment order)
- after atoms (`Atom.after`) — `decomposeMatch` lowers `>p` to the match plus a strict `Le r_p < XR` and `XL' = max(XL, r_p)`, with `XR` unchanged (the anchor meets `[r_p, top]`, so `p` need not overlap it). `decomposeEmit` gives `~>p` the anchor `(r_p, XR)` instead of `(l_p, r_p)`
- `expand` — top-level pipeline: exceptions → decompose → prune → split → filter → js-mode-resolve → delta-variants
- `expandStages` — same pipeline returning each named intermediate rule-list (`decomposed`/`split`/`filtered`/`resolved`/`variants`); `expand` is its `variants`. Used by the `v2-cli.ts` `--stage` dumps
- `decomposeJsRel` — js relations (plans/v2-js-relations.md): a plain match atom whose head names a `#js-def` relation pushes a `JsIterate` (args enter the chain as essential, like a match's user vars) and leaves the running anchor untouched — js relations are timeless, so no `Le`/`Max`/`Min` and no `_l_/_r_` slots. Every other appearance of a js-relation name throws: non-match markers and `not` here, exception LHS in `applyExceptions` — those all read tuples through paths a js relation never populates. Exception: a `!(...)` sub-atom naming a js relation is legal (plans/v2-js-rel-in-constrain.md) — `buildConstrainRowAtom` validates it (arity checked eagerly) and wraps it `*c-js` instead of `*c-plain`, so constraint-query enumerates the generator instead of reading the store. The `resolved` stage then runs `resolveJsModes` (js-rel.ts) on the post-split bodies, before delta variants (which only re-tag Match constraints)
- `applyExceptions` — source-to-source elimination of `{p t1..tn => e}` `Exception` atoms before any other pass: renames emitting `p` occurrences to a fresh `_<p>_prime<k>` across the working set, has the host rule broadcast its context via an internal *exact* `_<p>_ctx<k>` anchor emit (`Atom.exact`: lands on the running anchor itself, not a fresh left end; exceptions never gate `;` progression; LHS vars are exception-local, with prefix-bound ones re-unified via the ctx payload), and generates `<rule>_watch<j>` / `<rule>_exn<j>` / `<rule>_default<j>` rules around a flag relation `_<p>_exn<k>` (the `_exn` rule is skipped for an empty RHS — bare suppression). The watcher matches the primed tuple, *peeks* the context `(_<p>_ctx<k> U)` (overlap, not intersection) and raises the flag with an exact emit on the tuple's own interval; the flag is keyed by the intercepted tuple — the LHS terms with each wildcard freshened to `_t<i>`. The `_exn` rule matches the flag positively and re-peeks the ctx tuple to recover the prefix vars its RHS uses (so `e` runs on the tuple's interval); the default rule waits on an `exnCheck` of its own tuple's flag (`decomposeExnCheck`) and re-emits `p` exactly on the primed tuple's endpoints. Flags are plain tuples answered by a handler, not `#acc` rows: a chained exception's default re-emits at an already-settled moment, where acc rows are frozen (plans/v2-caret-fresh-left.md §5.2; earlier: plans/v2-exceptions.md, plans/v2-exception-watchers.md, plans/v2-exception-tuple-keyed-flags.md). Also invoked directly by `runFixpoint`. Sets `Program.provLinks`: one `{head, prime, arity}` record per default rule, derived from the *final* default-rule bodies (a later exception on the same relation renames an earlier default's emit head), consumed by `resolveExceptionProvenance` in fixpoint.ts (plans/v2-exception-default-provenance.md)
- `decomposeExnCheck` — lowers an exception default's `exnCheck` atom to a producer `Emit (_exn-wait (flag pat) idTpl)` at the running anchor and a consumer `Match (_exn-clear (flag pat) idTpl)` sharing the per-firing id (the one exception to the paired-Match construction); the exception-check handler (scheduler.ts) answers the wait row after inner-loop quiescence, so the anchor is unchanged
- `decomposeAccRead` — a plain match of an `#acc` relation in an ordinary rule lowers to `Match [name, pat…, _]` at `(XL, XL)` with the anchor unchanged (plans/v2-acc-relations.md §4.3): it samples the relation at the anchor's start, demands the rows there (eval.ts records the moment in `store.accDemand`), and is blocked until the acc handler has computed them. A `not r t̄` read (only on `#acc` relations; every variable already bound, else a compile error) lowers to a positive `Match [_acc-at, name, _]` at `(XL, XL)` — the marker the acc handler writes with `name`'s rows at a moment; reading it demands `name` at `XL`, blocks until its rows there are computed, and wakes the rule then, since an absent row produces no delta — followed by a negated `Match [name, pat…, _]` (`Match.negated`, never a delta position). Any other appearance of an acc relation throws — a non-match marker here, an exception LHS in `applyExceptions`
- `decomposeAccRule` — exported for acc.ts: lowers an `AccRule` to a flat body evaluated at one moment (plans/v2-acc-relations.md §4.1). The anchor is the Variable `_acc_m` (`ACC_MOMENT_VAR`, eval.ts); a stored-relation match becomes `Match [head, pat…, _id_k] at (_l_k, _r_k)` plus `Le _l_k _acc_m` / `Le _acc_m _r_k` (point containment, no Max/Min — the anchor never moves; the trailing `_id_k` binds the tuple's id for the firing identity); a read of another acc relation becomes `AccMatch` with a fresh moment Variable `_am_k`, and `not r t̄` a negated `AccMatch` (range-restricted; stratification is checked in acc.ts); js relations and `=` as usual. The head becomes one `AccContribute` (`accHeadTerm` enforces range restriction — every head Variable bound by the body, no `_` — and lowers `@js(...)`; an arity-0 op's column is the unit atom). No split, pruning or delta variants
- `decomposeRule` — anchor-decomposition pass; threads SSA anchor vars and a `*chain` fingerprint, lowering each `Marker` to post-expand atoms. `^p` (`decomposeEmit`, anchor case) mints a fresh left end like `+` — `XL < l < XR`, emitted on `[l, XR]`, the rule continues on `[l, XR]` — so a `^` reacting to state at `XL` starts strictly after it (plans/v2-caret-fresh-left.md §2); a rule-initial `^` (anchor still statically `(bot, top)`) and internal `exact` emits keep the old exact-anchor emit. `is` rows resolve choices: the harness's rule-initial `^ is T V` is emitted as the input row `_is-input T V` (installed by scheduler.ts `isInputHandler`), and any other emit of `is` is a compile error. The ask case emits `_choose chooseId (atom) actor` (actor Symbol from the ask atom, default `you`) and statically rejects asking an already-bound variable (`state.seen` is the bound-so-far set) — an ask introduces only fresh choice variables (plans/v2-choice-actors.md). `?` and `!` rows are emitted at the running anchor `(XL, XR)` — no fresh moment, anchor unchanged (plans/v2-choice-components-by-moment.md) — so a choice is asked at the moment its rule has reached and a `!` next to its `?` sits at that same moment. An `#acc` relation inside `!(...)` is an ordinary `*c-plain` sub-atom (arity checked); `not r t̄` there becomes a `*c-not` sub-atom (acc relations only; its variables bound by the rule or by a positive sub-atom of the block)
- `splitRule` — slices a rule at every `Emit` into producer/consumer halves
- delta-variants — semi-naive cloning; tags one (non-negated) `Match` as `delta` and sets `deltaHead`/`deltaSafeSkip`
- fresh Id templates — per-firing fingerprint templates `*id`/`*var`/`*choose`/`*mom`
- reserved symbols — `*chain`, `*conj`, `*c-plain`/`*c-js`/`*c-not`, `_constrain`, `_dead-choice`, `_acc-at`, `_exn-wait`/`_exn-clear`/`_exn-held`, `_is-input` (consumed downstream by scheduler/constraint-query/acc)

# expand-liveness.ts

A backward-pass chain-liveness optimization run between `decomposeRule` and `splitRule`: it prunes non-essential, dead chain Variables out of `(*chain ...)` fingerprint templates and removes dead `max`/`min` anchor-SSA definitions. Pruning preserves correctness because producer/consumer split halves share the same (smaller) `idTpl` objects, so structural unification still recovers the surviving chain vars; essential identity-bearing vars are always kept to avoid dedup collisions.

**Key terms:**
- `pruneChains` — backward liveness pass; drops dead chain Variables from `*chain` templates and dead `max`/`min` anchor defs
- `live` / `essential` — downstream-referenced names vs. identity-bearing names that must be retained

# eval.ts

The single-rule evaluator: a CPS-style backtracking interpreter over the flat post-expand `RuleAtom` primitives, mutating a `Store` by matching stored tuples and emitting new ones. All anchor manipulation is now explicit IR, so this is a flat dispatch over `Match`/`Emit`/`Le`/`AssertLt`/`Equal`/`JsIterate` (an `AssertLt` of `top < x` or `x < bot` fails the firing instead of recording an edge; an `Equal` computes its `max`/`min`/`@js` rhs first, then unifies; `max`/`min` of incomparable moments fail the match, or in lattice mode return a lattice-node moment) (plus `AccMatch`/`AccContribute` inside acc rules) with a binding trail for backtracking; pre-expand atoms reaching it throw.

**Key terms:**
- `evaluateRule` — public entry; runs the CPS backtracking interpreter, mutating the `Store`. Takes an optional `AccEvalCtx` for lowered acc rules; its `tupleBound` (a moment's watermark, acc.ts) makes every stored-tuple `Match` stop at that tuple index (candidate buckets are in insertion order); its `cone` (store.ts `momentCone`) answers each `Le` with the acc moment on one side from two precomputed sets instead of `comparable`/`lessEq`
- `matchCandidates` / `accRowCandidates` / `argPlan` — which candidates a `Match` / `AccMatch` scans. Each atom's *plan* is fixed on its first evaluation: the argument positions ground there (plus 0 for a `Match` whose left endpoint is). Body order is fixed, so the bound pattern is the same every time; an evaluation that finds a planned position unground just scans. A `Match` with a plan beyond the left endpoint alone probes the store's argument index (store.ts `argIndexFor`), else the (head, left end) / head bucket; an `AccMatch` probes an index over its rows array, cached per array (rows arrays are replaced each round, never mutated; arrays under 8 rows are scanned). Only which candidates are visited changes, never their order or the result
- `AccEvalCtx` / `AccRow` / `ACC_MOMENT_VAR` — what an acc rule needs from acc.ts (plans/v2-acc-relations.md §5.3): `rows(relation)` (the local rows of the relations it reads: key/value terms plus the row's moment) and `contribute(relation, terms, moment, firing)`. `evalAccMatch` unifies the pattern against `[relation, ...row.terms]` and the moment Variable against the row's moment as a backtracking choice point; `evalAccContribute` substitutes the head terms, takes the lub of the matched tuples' lefts and matched acc rows' moments (the moment being resolved, bound to `_acc_m`, if no lub exists), joins the matched tuple ids into the firing identity, and calls `contribute`. Both throw outside an acc rule
- `evalSeq` — dispatches on atom tag and chains continuations over a binding trail (unwound on backtrack)
- `evalJsIterate` — enumerate a `#js-def` relation (plans/v2-js-relations.md): decode the resolved clause's `+`-position args, run its generator, unify each yielded array against the `-`-position arg terms as a backtracking choice point (a bound `-` arg filters). Steps the iterator manually so continuation errors (GasError) propagate unwrapped while user-body errors surface with the relation name; `JS_REL_YIELD_CAP` guards runaway generators
- acc demand and consulted-moment recording — a `Match` whose head is in `store.accRelations`, or is `_acc-at r` (`ACC_AT_HEAD`, a `not r` read's marker), demands that relation at its (bound) left endpoint (`demandAcc`: `store.accDemand`, served by acc.ts) before scanning candidates, so a read that matches nothing — or finds no rows yet — still asks for them. An acc-relation read also records the moment in `store.accConsulted` (display-only, acc-view.ts). Acc rules read through `AccMatch` and never land here
- semi-naive gen filter — a `Match`'s `delta`/`old` `MatchConstraint` filters candidates by generation
- negated reads — a `Match` with `negated` (expand.ts `decomposeAccRead`) succeeds once, binding nothing, iff no stored row unifies at its endpoints; an `AccMatch` with `negated` does the same over the local rows of a strictly lower acc stratum

# js-values.ts

The single Term ↔ JS value boundary for user-defined `#js` functions (see `plans/v2-user-js-functions.md`): `decodeTerm` lowers a ground Term to a plain JS value for a `JsCall` argument, and `encodeTerm` lifts the return value back to a raw (un-hashconsed) Term. Compounds map to arrays, symbols to strings, numeric symbols to numbers, and booleans encode to the symbols `1`/`0`.

**Key terms:**
- `decodeTerm` / `encodeTerm` — ground `Term` → JS value (expanding `Ref`s) and JS value → raw `Term`
- term↔value mapping — compound ⇄ array, non-numeric Symbol ⇄ string, numeric Symbol → number, boolean → Symbol (encode-only)

# js-rel.ts

js relations (`#js-def`, plans/v2-js-relations.md): mode selection and clause compilation. A js relation is a set of generator clauses over one name/arity, each with a mode vector (`+` = bound at call, a JS parameter; `-` = enumerated, yielded). Modes are ordered `- < +` pointwise; `resolveJsModes` — run in `expandStages` between `filtered` and the delta variants, on the post-split flat bodies — does a left-to-right binding analysis per rule and stamps each `JsIterate` with the earliest declared clause ≤ the call site's modes (a `-` clause position serves a bound argument by yield-then-filter; no clause → compile error naming the rule and modes). Post-split is what makes cross-slice bindings visible: a consumer slice's leading Match unifies the stored row's trailing idTpl, so recovered chain variables count as bound.

**Key terms:**
- `resolveJsModes` — per-rule left-to-right binding analysis (Match/Emit bind everything they mention; Equal binds one side when the other is fully bound, and always binds the lhs of a computed max/min/@js rhs) + earliest-clause selection; sets `JsIterate.defIndex`
- `compileJsRels` / `CompiledJsRel` — compile each clause's body once via the generator-function constructor with the `+` params as JS parameters; consumed by `evalJsIterate`
- `JS_REL_YIELD_CAP` — per-call yield limit (no tuple is emitted between yields, so gas can't interrupt an infinite generator)

# builtins.ts

Built-in relations every program gets without a declaration. Today: the numeric comparisons `lt` / `gt` / `le` / `ge`, defined as js relations with one `+A +B` clause each, so they inherit js-relation semantics wholesale — timeless (no anchor effect), both arguments must be bound at the call site (`resolveJsModes` reports an unbound one as the usual mode error), legal as a `!(...)` option filter, and rejected as an emit head, a `not` read, or an exception LHS. The atom succeeds, yielding once and binding nothing, iff the comparison holds on the two decoded JS numbers; a non-numeric argument (a name, a compound, a Peano nat) is a runtime error naming the relation. `parseProgram` seeds `Program.jsRels` from `builtinJsRels()` and rejects any user declaration of the same name (`#js-def`, `#js`, `#acc`) with a "built-in relation" error at the declaration's line; `renderProgram` (print-ir.ts) skips the seeded clauses via `JsRelDef.builtin`.

**Key terms:**
- `builtinJsRels` — a fresh `Map<string, JsRelDef[]>` of the seeded clauses per parse (user clauses are pushed into these arrays, so they must not be shared)
- `isBuiltinRel` — membership test used by the parser's reserved-name checks

# store.ts

The v2 store: interval-bearing hashconsed tuples, head indexing, and the moment-order (partial-order) relation. It provides tuple insertion with dedup/gas/semi-naive bookkeeping, order-edge assertion (two strategies, lazy "old" vs "eager" forward-closure), reachability/comparability queries over moments, interval overlap/containment tests, and least-upper-bound (join) computation.

**Key terms:**
- `Store` / `createStore` — central state (hashcons table, tuples, head index, moment partial-order, gas, semi-naive generations, stats); factory seeds `bot`/`top`
- `intern` / `tokenOf` — hashcons wrappers; token = integer `Ref` id
- `addTuple` — interns and inserts a tuple with dedup, gas check, head bucketing, generation tracking
- `addOrder` — asserts a moment-order edge `lt < gt`; records the immediate predecessor in `orderBwd` under both strategies (moment-walk.ts computes its frontier from it)
- **Creation-time ordering invariant** — the evaluator only asserts order edges involving a moment as it is created: an emit places its fresh `l`/`r` inside a window already known to satisfy `XL < XR` (strict matches never leave a point window), and the scheduler's handlers add tuples only at existing endpoints (acc rows at `[m, m]`, `is` rows from their choice's ask moment, exception answers on the waiting row's interval), asserting no new edges. So an edge never orders two pre-existing moments that weren't already ordered: once two moments exist, their comparability is fixed for the run. Not enforced in code; lattice mode relies on it
- `StoreOptions.lattice` / `latticeMax` / `latticeMin` / `latticeNodes` — moment-lattice mode (off by default; `runFixpoint(..., { lattice })`, `v2-cli --lattice`, `?lattice` in the web page URL). `max`/`min` of incomparable moments build a `(*max …)`/`(*min …)` lattice-node moment instead of failing the match: elements flattened, units (`bot` for max, `top` for min) dropped, reduced to an antichain, sorted by token, so equal joins/meets share a token; comparable arguments collapse to the larger/smaller one (deterministic by the invariant). A node is wired into the order graph when it's created — a join gets edges from its elements and to the minimal common upper bounds, and a meet gets edges to its elements and from the maximal common lower bounds (plus covering older same-kind nodes) — so the moment walk and timeline treat it as an ordinary moment. `≤` is decided by `latticeLe`: a join is ≤ b iff all its elements are, a ≤ a meet iff a ≤ all its elements, otherwise reachability. Asserts stay conjunctive: `+ j < l` puts `l` after every element of `j`, and `+ m < l` puts it after every common lower bound of `m` — weaker than "after one of them", which would be a disjunction
- `settled` — moment tokens whose `settle` hooks have run (the walk was quiet there; the acc snapshot is fixed — `accWatermark`). A superset of `resolved`: a moment with a pending choice is settled but not resolved
- `resolved` — moment tokens the moment walk has resolved (a down-set of the order; in-memory, every run starts from a fresh store)
- `argIndex` / `argIndexFor` / `argKey` / `groundStored` — argument indexes: per head and set of term positions (1 = first argument; 0 stands for the left endpoint, the head being fixed per index), the head's tuple indices bucketed by the tokens at those positions, in insertion order (so a watermark bound still ends a scan). Built from the head bucket on first request, then maintained by `addTuple`. A tuple whose argument at an indexed position is not ground would unify with any probe, so it makes the index unusable and lookups fall back (stored tuples are ground in practice). `useArgIndex` (`createStore({ argIndex })`, default on; `runFixpoint` `argIndex: false` turns it off for A/B checks)
- `accRelations` / `accConsulted` — `#acc` display bookkeeping (plans/v2-acc-timeline-display.md): the declared acc relations with a static `readByRules` flag (set by `runFixpoint`: some expanded ordinary rule has a `Match` on the head), and per relation the moment tokens at which an ordinary rule's point read was attempted, matched or not (recorded by `evalMatch`). `accConsulted` is never consulted by evaluation; a non-empty `accRelations` switches on demand recording in `evalMatch`
- `accDemand` / `accPending` / `accComputed` / `accWatermark` / `demandAcc` — demand-driven `#acc` evaluation (acc.ts), per relation: per moment, the relations asked for there (an ordinary acc read, a `not r` read's `_acc-at r` read, a `_constrain` row's moment for the relations a `!(...)` reads, or a rule-initial read's `bot`, statically); the moments with a demanded relation not yet computed; per moment, the relations computed (demanded ones plus what their acc rules read); and per settled moment the watermark `tuples.length` at its settle. Rows at `m` are a pure function of the tuples below the watermark — the store is append-only and, by the creation-time invariant, whether an old tuple is alive at `m` never changes — so computing them later gives the settle-time snapshot. `demandAcc(store, tok, relation)` adds a relation at a moment (the moment is pending unless the relation is already computed there)
- `momentCone` / `coneLe` — the moments at or below / at or above `m` (two walks over `orderBwd` / `orderFwd`, bot/top implicit), built once per `computeAccAt`. `coneLe` answers `a ≤ b` with `m` on one side exactly as `lessEq` would; it replaces the per-tuple `l ≤ m`, `m ≤ r` checks, which re-walked each `l`'s closure whenever newer moments existed than its cached one (`ltClosedAt`). Not built in lattice mode or under the eager order strategy
- `lessThan` / `lessEq` / `comparable` — strict/non-strict order and comparability over moments (`bot`/`top` sentinels); in lattice mode `a < b` is `latticeLe(a, b) && !latticeLe(b, a)`
- `intervalsOverlap` / `intervalContains` — interval overlap and containment tests
- `candidatesByHead` — head-symbol-indexed tuple lookup (the match index)
- `leastUpperBound` — join over the moment lattice (`null` when ≥2 incomparable minimal upper bounds)
- `GasError` / `ORDER_STRATEGY` — tuple-budget exhaustion sentinel; lazy-`"old"` vs eager order-maintenance switch

# moment-walk.ts

The scheduler's interface for calculating things along the moment order (plans/v2-moment-walk.md). A Turn program has a monotone part (the rules, run to quiescence by fixpoint.ts's inner loop) and a non-monotone part (`#acc` rows, `not` reads, exception defaults, choice resolution) that must observe a *complete* state at a moment. The walk stratifies the non-monotone part by the temporal order the monotone part computed: after each monotone fixpoint it takes the **frontier** — the minimal unresolved moments — and runs every registered `MomentHandler` at each of them. A handler may add tuples (`progress`), may be waiting on the outside world (`blocked`, a `you` choice), or may have nothing to do. A moment is marked **resolved** once a round makes no progress anywhere and no handler is blocked at it. The walk knows nothing about aggregates or choices; those are the handlers in scheduler.ts.

The moment set is every endpoint the store has seen (`store.momentTerms`) except `top`; `bot` is a moment (rule-initial `^` emits live at `(bot, top)`, and a rule-initial acc read samples there). `store.resolved` is kept as a **down-set** of the order, which is what lets the frontier be computed from asserted predecessor edges alone: a moment is minimal iff every immediate predecessor in `store.orderBwd` (plus the implicit `bot`) is resolved. That edge test only ever *excludes*, and it excludes cycle members forever (the `"old"` order strategy never rejects a cycle; `a, (+p); +q` asserts one through a point anchor), so an empty edge-based frontier with moments still pending falls back to quadratic minimality under the strict order, which resolves a cycle as a unit.

**Key terms:**
- `MomentHandler` — `{ name, run(store, m) → { progress, blocked }, demanded?(store), exclusive?, settle?(store, m) → boolean }`; `run` must be idempotent. An `exclusive` handler completes the monotone state rather than judging it: it runs first in every round, at its own `demanded` moments only (whatever their state), and a round in which it adds a tuple runs no other handler, so the inner loop's readers see its rows before anything is judged (the acc handler serving late demand). `settle` is called by `settleMoments` once per moment, the first time a walk round with the moment on the frontier is quiet — after its folds have settled, before it is marked resolved and before any choice at it surfaces. So a moment passes through: created → folds quiet → **settled** (`store.settled`) → resolved (plans/v2-choice-components-by-moment.md step 6). The acc handler fixes its snapshot (and writes demanded rows) in `settle`
- `unresolvedMoments` / `frontier` / `markResolved` — the moment set minus `resolved` and `top`; its minimal elements (edge test, strict-order fallback); marking
- `runWalkRound` — one round: first each `exclusive` handler at its demanded moments (progress there returns at once, frontier empty); then frontier ∪ late demanded moments (resolved ones some non-exclusive handler demanded), every non-exclusive handler at each; returns a `WalkRound` (`frontier`, `late`, `progress`, `blocked`, `exhausted`). Marks nothing — fixpoint.ts decides
- `settleMoments` — run every handler's `settle` at each not-yet-settled moment given, recording them in `store.settled`; true iff any added a tuple (fixpoint.ts then re-enters the inner loop so readers of the new rows fire — they may emit at the same moment, even a new `?`)

# acc-ops.ts

The `#acc` op registry (plans/v2-acc-relations.md §2.2, §5.5). Every aggregation op is a commutative monoid `(M, ⊕, e)` with two maps — η (`inject`: one contribution → monoid element, the unit of the free commutative monoid on values, which is why contributions form a *bag*) and ρ (`readout`: monoid element → zero or more value terms, the one coercion from "a value per key" to "rows of a relation"):

| stage | `@sum` | `@count` | `@min` | `@last` | `@arg-min` | boolean |
|---|---|---|---|---|---|---|
| η inject | a | 1 | a | {(t, a)} | {(a, n)} | true |
| ⊕ combine | + | + | min | ∪, keep temporal maxima | ∪, keep minimal n | ∨ |
| e identity | 0 | 0 | ∞ | ∅ | ∅ | false |
| ρ readout | {s} | {n} | {v}; ∞ ↦ ∅ | the set | the set | true ↦ {()}; false ↦ ∅ |
| idempotent | no | no | yes | yes | yes | yes |

Single- vs multi-valued is a property of ρ, not of the op; identities without a term read out as ∅; a keyless relation's zero row is `ρ(e)`; recursion through an op has a least fixpoint iff ⊕ is idempotent. One term representation per op: `@sum` reads numeric Symbols (the `sum` aggregator), `@count`/`@min`/`@arg-min` are Peano (`z` / `(s X)`, via `natValue`); η rejects the other spelling. **Adding an op**: (1) fill in a column of the table — if ⊕ is not commutative and associative it is a relation computed by an acc rule, not an op; pick one term representation; (2) add the entry to `ACC_OPS` — `AccOp` widens automatically and parse.ts/expand.ts read `arity` and `column`, so no parser change; `inject` throws on out-of-domain terms naming the term, `combine` keeps a canonical representative if the carrier admits several spellings, `readout` must not depend on combination order, `idempotent` must be truthful; (3) add samples to the law harness in `v2_acc.test.ts` (an entry without samples fails it); (4) add the op to the tutorial.

**Key terms:**
- `AccOpDef<M>` — `{ name, arity (0 | 1: does η take the head term?), column (rows carry a value column; false only for boolean), inject, identity, combine, readout, idempotent, internal? }`
- `ACC_OPS` / `AccOp` / `accOp` — the registry (`sum`, `count`, `min`, `last`, `arg-min`, and the internal `bool` that a declaration without an agg column uses), its key type, and the lookup (internal entries hidden unless asked for)
- `natValue` / `UNIT` — Peano reader (null for anything else, numeric Symbols included); the unit atom `()` an arity-0 head writes and boolean's ρ yields

# acc.ts

`#acc` relations: a snapshot per settled moment, computed where something reads it (plans/v2-acc-relations.md; timing from plans/v2-choice-components-by-moment.md). An acc relation's rows are a function of the state alive at a moment: `body / head` rules derive contributions from the stored tuples alive at `m` (interval contains `[m, m]`) and from other acc relations' rows at `m`, the declared op folds them per key (`ρ(⊕ᵢ η(cᵢ))`, generic over the acc-ops.ts registry — no op-specific code here), and the result is written as point rows `name k… v <id>` at `[m, m]` with a deterministic `(*acc name k… v m)` id. Ordinary rules read them with a point match at their anchor's left endpoint (expand.ts `decomposeAccRead`). Evaluation stratifies the acc relations over their read dependencies (edge r → s when a rule with head s has an `AccMatch` on r; Tarjan's SCCs in dependency order), evaluates each stratum's lowered rules with `evaluateRule` under an `AccEvalCtx` (the body prefixed with `Equal _acc_m m`), and iterates a recursive stratum to a fixpoint with accumulating contributions — deduplicated by (key tokens, value token, moment token, firing identity), so two `hit x 3` facts both reach `@sum` while idempotent ops are unaffected. When every op in the SCC is idempotent that is a least fixpoint; otherwise the program is assumed well-defined and `ACC_ROUND_CAP` turns divergence into an error naming the stratum and moment. A keyless relation folds its single group even when empty (the zero row); a keyed relation has no row for absent keys. Each row records a moment (the readout's, or the group's lub) for downstream `@last` folds.

**Timing.** The snapshot at `m` is fixed by the handler's `settle` hook, which fires once per moment, the first time a walk round with `m` on the frontier is quiet: after every rule firing that the state below `m` enables has run, before `m` is marked resolved, and before any choice at `m` surfaces. It records the watermark `store.accWatermark[m] = tuples.length`; the rows at `m` are a function of the tuples below it (store.ts), so they are the same whenever they are computed. Rows written are progress, so the inner loop runs and readers at `m` fire — and acc at `m` is written once. Since a non-initial `^`, like `+` and `~`, mints a moment strictly after its anchor's start (plans/v2-caret-fresh-left.md §2), what those readers (or a choice's continuation) emit starts after `m`: the rows written at a settled `m` agree with the final store at `m`, which is what makes `not` reads sound. Acc at a choice's moment is therefore the state from *before* the choice, which is what lets a `!(...)` block read it (the block's ordinary stored-tuple match admits the point row at the component's moment); a second choice chained at the same moment sees the acc state from before the first.

**Demand.** Under `runFixpoint`'s default `accMode: "demand"` a relation's rows are computed only at moments it is demanded (`store.accDemand`, per relation): an ordinary acc read or a `not r` read's `_acc-at r` read (eval.ts `evalMatch`), a rule-initial such read at `bot` (statically, fixpoint.ts — the empty-delta skip would never run that rule), or — for the relations some `!(...)` reads (`constrainReads`) — every `_constrain` row's moment, so a component's rows exist before it is enumerated (scanned with a cursor over the `_constrain` bucket). Computing a relation computes everything its acc rules read (`accClosure` over `CompiledAcc.reads`; only the strata holding those relations run, `computeAccAt`'s `only`); a relation demanded later at the same moment recomputes its shared dependencies from the same watermark, and `addTuple` dedups their rows. `settle` computes at once what `m` already demands; demand at an already-settled moment is served from the watermark through `demanded` / `run`, and the handler is `exclusive` (moment-walk.ts), so readers of those late rows fire before any other handler judges the state — the run reaches the ordinary tuples eager mode does. Rows of a relation nothing reads at a moment are never computed there, so an op error or round-cap divergence there does not surface. `accMode: "eager"` computes every relation at every settled moment (`v2-cli --acc-eager`, web `?acc=eager`: acc bars at every moment). The web page runs demand mode; its moment inspector fills in the relations the run did not compute through `FixpointResult.accAt` (`accRowsAt`: every relation at a settled moment from its watermark, written nowhere).

**Key terms:**
- `compileAcc` — lower every acc rule (`decomposeAccRule`), resolve js modes, build the dependency graph and strata (`CompiledAcc`: `decls`, `strata` of `{ relations, rules, recursive }`). Stratified negation: a negated `AccMatch` (`not r` in a rule for `h`) must read a relation outside `h`'s SCC, else a compile error
- `computeAccAt` — the rows of every acc relation at a point `m` (`Map<relation, AccRow[]>`), stratum by stratum; an optional `bound` (the watermark) limits the stored tuples read to indices below it
- `accHandler` / `AccHandlerOptions` / `AccMode` — the `MomentHandler` (`mode` eager or demand — eager by default at this level, demand under `runFixpoint`; `markers`, the relations some `not` reads; `constrainReads`, the relations some `!(...)` reads). `settle` records the watermark and computes what is wanted at `m` — every relation when eager, else the demanded ones not yet computed, closed under `accClosure` — writing their rows and, for each one in `markers`, an `_acc-at r <id>` point row at `[m, m]`, which a `not r` read demands, waits on and is woken by. `demanded` returns pending settled moments; `run` computes what is pending at one of them from its watermark
- `accClosure` — relations plus every acc relation they read, transitively (`CompiledAcc.reads`)
- `accRowsAt` — inspection only: every relation's rows at a settled moment from its watermark, nothing written (`FixpointResult.accAt`, memoized per moment)
- `ACC_ROUND_CAP` — rounds a recursive stratum may take at one moment before the run fails

# acc-view.ts

Display-side views of `#acc` rows (plans/v2-acc-timeline-display.md). DOM-free. In eager mode (acc.ts) the engine stores every acc relation's rows as point tuples at every settled moment, so a value that holds for a while is stored once per moment; nothing here changes that (under demand — the web page's default — a relation has rows only where it is read, and the bars fragment accordingly) — these functions fold the repetition back up for display.

`accRuns` merges each distinct row content (the row's user terms; the trailing id names the moment and is left out) into bars. It computes the Hasse covers of the asserted moment order (`bot` included, `top` excluded, non-cover asserted edges dropped via `lessThan`, cycles tolerated), and per content covers the moments it holds at greedily with chains along a linear extension: a moment extends a chain whose last moment it covers, otherwise it starts a new one. A chain's bar runs from its first moment — or from the fork moment, when it branches off another bar of the same content — to where it stops: the successor at which the content merges into another bar, else the first resolved successor (the value ended there; a closed edge), else the first unresolved successor or `top` (`open`: not "ended" but "not computed past here", e.g. blocked behind a choice). On a linear timeline that is one bar per stretch a value holds; on a branching one, a bar per branch. A bar over-approximates in one way: it runs through every column between its endpoints, including side-branch moments where the content does not hold — the ambiguity any episode bar has against incomparable moments.

**Key terms:**
- `accRuns` / `AccRun` — the merged bars: relation, `tupleIndex` of the row at the first moment, `lTok`/`rTok`, `open`, the `moments` held at, and `consulted` (the subset where `store.accConsulted` records a read)
- `accRelationVisible` — a per-relation override wins; otherwise a relation shows iff some ordinary rule reads it (pure intermediates start hidden)
- `isAccRow` — a point tuple of a declared acc relation
- `accSnapshot` / `AccSnapshot` — the moment inspector's data: every relation's rows at one moment, each `new` when some immediate (resolved) predecessor lacks it, plus the `gone` rows a predecessor has and this moment lacks, the `consulted` flag, and whether the moment is resolved. Each relation's `source` says where its rows come from: `run` (computed by the run here, `store.accComputed`), `inspect` (filled in by the optional `inspect` function — the fixpoint result's `accAt` — at the moment and at the predecessors diffed against; `tupleIndex` -1), or `none` (demand mode, nothing read it here). A predecessor whose rows are unknown is left out of the diff. Ignores timeline visibility

# fixpoint.ts

The top-level evaluation driver. It expands a program, runs an inner loop firing all rules to quiescence (semi-naive), then runs the moment walk (moment-walk.ts): rounds of handlers at the frontier. A round that adds tuples hands back to the inner loop (`iteration++`, so the new rows are the next delta). A round that adds nothing first runs the handlers' `settle` hooks at the frontier moments that have not settled yet (`settleMoments`; the acc handler fixes its snapshot here and writes demanded rows — if any were added the loop hands back to the inner loop so readers fire), then resolves its unblocked frontier moments, and otherwise the walk continues *without* re-running the rules — nothing changed — so a program with no pending work at a moment crosses it for the cost of a frontier computation. Only when every frontier moment is blocked on a choice does the loop surface the choices there: `computeComponents` for the chooses at the blocked moments (components are located at their ask moment, so nothing asked later is pulled in; a misplaced constraint is the `late-constraint-error` status, also checked at `done` via `checkConstrainPlacement` for choices a saved `is` row resolved before they surfaced; `describeErrorStatus` words the error statuses for hosts), the empty-fringe error, dead-choice marking, and rng auto-resolution, unchanged. `exhausted` (every moment resolved, nothing demanded) is `done`. Gas exhaustion is caught and surfaced as a `gas` status. The old `!progressed → done` safety net is gone: no progress simply means the moment resolves, which is the correct reading of an aggregate with an empty fold.

**Key terms:**
- `runFixpoint` — public entry; expands the program, compiles `#js`/`#js-def` bodies (`compileJsDefs`/`compileJsRels`), builds the handler list (`isInputHandler`, `choiceHandler`, `exceptionCheckHandler`, `accHandler` — the last with `mode` from `options.accMode` (default `"demand"`), `markers` the relations of the expanded rules' `_acc-at r` matches, i.e. those some `not` reads, and `constrainReads` the acc relations a `_constrain` emit nests), seeds `store.accRelations` (each declared acc relation, `readByRules` iff an expanded rule matches on it), demands `bot` statically for a rule whose first match is an acc / `_acc-at` read (a non-ground one instead clears the rule's `deltaSafeSkip`), runs the loop, returns a `FixpointResult` (`{ store, iterations, status, rules, accAt }` — `rules` are the expanded rules the loop ran, used by `print.ts:tupleBindings`; `accAt` computes any relation at a settled moment for inspection); catches `GasError` → `gas`; `options.lattice` creates the store in moment-lattice mode (store.ts)
- `resolveExceptionProvenance` — post-fixpoint `tupleSource` fixup on every return path (including `gas`): an exception default rule re-emits a matched `_<p>_prime<k>` tuple with identical args and endpoints (only head + trailing id slot differ) but its Emit's static span is the exception's line; this pass re-attributes each tuple of a `Program.provLinks` head to the span of its structurally matching prime tuple, following links transitively for chained exceptions, keeping the tuple's own span when no match exists (emits that escaped renaming: off-arity). So `tupleSource` is not always the firing Emit's span (plans/v2-exception-default-provenance.md)
- inner loop / outer loop — fire all rules to quiescence, then walk the moment order (above) until a handler adds tuples (re-enter) or the frontier is fully blocked (surface choices). A component with **zero option tuples** never surfaces: under the temporal-monotonicity assumption (the component is evaluated at its quiescent moment `M`, and no later emission's interval can contain `M`) it can never gain options, so every active term is marked dead via a `_dead-choice <term>` row (`markDeadChoice`) and the loop re-enters — the owning asks stop blocking, no `is` row ever appears, and their `.is` continuations simply never fire (Ceptre's "transition not applicable"). Applies to `you` and `rng` components alike. Components whose controlling (highest) actor is `rng` don't surface: `resolveRngChoice` commits them and the loop re-enters; mixed components surface for the user's `you` terms first (plans/v2-choice-actors.md). `runFixpoint` accepts `options.random` (seedable) and reports every roll in `FixpointResult.rngCommits` so the harness persists them as `^ is` rows (web-v2 appends them, gated on the source being unchanged since the run started). The stream is latched at the first roll: an explicit `options.random` wins, else a program seed (`+ rng-seed n` via `programSeededRandom`), else `Math.random`; later `rng-seed` tuples have no effect
- delta-safe skip — skips rules with empty deltas via `deltaSafeSkip`/`deltaHead`/`prevHeads`
- run-once rules — `runFixpoint` marks a rule whose body reads nothing from the store (`readsNothing`: no match of any kind, no `≤` or `max`/`min` — those consult the growing moment order — only term / js `=`, emits, order assertions, js relations) `Rule.runOnce`; `innerLoop` evaluates each such rule once per run (`ranOnce`) instead of every sweep. A saved choice (`= V… ^ is …`) is one: re-running it only re-derived its row, and with a rule per saved move and more sweeps per longer game that grew quadratically

# scheduler.ts

The non-monotone part of a program apart from `#acc` (acc.ts), packaged as moment handlers for the moment walk (moment-walk.ts, plans/v2-moment-walk.md). Three handlers: **choice inputs** install the harness's `is` rows at their choice's ask moment, **choices** report a moment blocked while an unresolved `_choose` row starts there (surfacing itself stays in fixpoint.ts), and **exception checks** answer the default rule's wait rows. `#agg`, `#reactive` and bracket aggregation, with their demand/reactive handlers, were removed (plans/v2-caret-fresh-left.md §5.4).

**Choice inputs** (plans/v2-caret-fresh-left.md §6.3): a choice's resolution `is T V` lives on `[l, top]`, where `l` is the ask moment — the left end of `T`'s `_choose` row. A rule reading `is T V` therefore narrows to start at or after the ask moment: the asking rule's continuation and any rule that reached `T` after the ask proceed, while a rule anchored on an episode that ended before the ask cannot read the value and place a consequence in the past. (A fresh moment strictly after the ask was rejected: it is incomparable to the ask's other consequences, so a `cell-choice C, is C V` join would fail.)

**Key terms:**
- `isInputHandler` / `installIs` / `SYM_IS_INPUT` — the harness's rule-initial `^ is T V` reaches the store as `_is-input T V` (expand.ts); the handler installs each pending input as `is T V` at `[ask.l, top]` when the walk reaches its ask moment (`demanded` covers late ones). `installIs` is shared with rng commits
- `exceptionCheckHandler` — answers each `_exn-wait (flag pat) id` row (expand.ts `decomposeExnCheck`) once, with `_exn-clear` when no `flag pat` tuple is alive at the row's left end and `_exn-held` otherwise. Handlers run only after the inner loop is quiet, so every watcher that can flag the tuple has fired; a wait row at an already-settled moment (a chained exception's default re-emitting at the tuple's own start) is `demanded`
- `choiceHandler` — reports a moment blocked while an unresolved `_choose` row starts there; a late choose row at a resolved moment is `demanded`
- `collectBlockedChooses` — `_choose` rows with unresolved active terms (reading the actor column at terms[3], defaulting `you`)
- `markDeadChoice` / `resolvedChoiceTokens` / `_dead-choice` — dead-choice resolution: the fixpoint loop marks each active term of a zero-option component with a `_dead-choice <term>` row at `(bot, top)`; `resolvedChoiceTokens` treats those markers as resolutions alongside `is` rows (constraint-query's `gatherChoiceContext` reads them the same way, with no substitution value — a constrain pattern still mentioning a dead term can never match, so entangled survivors die on a later round)
- `resolveRngChoice` / `RngCommit` — auto-resolve one all-`rng` component (plans/v2-choice-actors.md): pick one option tuple uniformly at random (uniform over joint assignments) and commit every active term with `installIs` (an `is <term> <value>` row from the ask moment, with a `(*rng <term>)` trailing id); returns null on zero options
- `programSeededRandom` / `mulberry32` — program-provided rng seed: the user relation `rng-seed` with one numeric argument (`+ rng-seed 42`, asserted once at startup) yields a deterministic mulberry32 stream; distinct values or a non-numeric argument are errors, duplicates of one value are fine

# constraint-query.ts

Per-component option enumeration for active choices (the `?`/`choose` mechanism). Components are **located at their ask moment** (plans/v2-choice-components-by-moment.md): `?` and `!` emit their `_choose` / `_constrain` rows at the rule's running anchor without minting a moment, a choice term's ask moment is its choose row's left endpoint, and a constrain row belongs to the moment it sits at. When the moment walk is blocked at moments `B`, the seed terms are the unresolved terms asked at a moment of `B`; a row is *ready* when every unresolved term it touches (after `is` substitution) is a seed term asked at the row's own moment; components are the connected components of seed terms over ready rows, each with one moment `m`, and a backtracking conjunctive query evaluates every sub-atom at `m` to produce deduped option tuples. There is no closure to other moments: a row that also touches a term asked later is *deferred* to that later moment, where the earlier term is already bound — so choices are resolved in temporal order and a component never depends on tuples derived at a later moment (monotonicity). `m` is a settled frontier moment, so the state the query reads is final, and acc rows at `m` exist.

**Placement.** A row must sit at the ask moment of the latest choice term it mentions (resolved or not), with every other mentioned term asked at or below it. Otherwise: `late` (an anchor-advancing atom between the `?` and the `!`) or `entangled` (terms asked at incomparable moments). Checked for every row before components are built, memoized per store (`placedRows`).

**Key terms:**
- `computeComponents` — main export; returns `ComponentOptions` per component (including per-active-term `actors`, from each term's owning choose row via `actorByTok`), or `empty-fringe-error` (`deferredOnly` when the term's only rows also mention a later ask), or `late-constraint-error`
- `checkConstrainPlacement` / `ConstraintPlacementError` — the placement check over every `_constrain` row, for the end of a run
- `gatherAskMoments` — choice term token → ask moment, from every `_choose` row
- `ConstrainRow` — a parsed `_constrain (*conj …)` row (sub-atom `kind` plain/js/not): `touched` unresolved active tokens, `mentions` (every choice term, from the atom before substitution), and its left endpoint
- `RawComponent.moment` — the component's moment: its members' ask moment, where its rows sit
- `runComponent` — backtracking conjunctive query producing deduped option tuples; the component's sub-atoms are flattened into one list with `*c-js` subs scheduled after the store-backed ones and `*c-not` subs last (a component is semantically one conjunction, so order only affects mode availability and boundness — js-last maximizes boundness and makes behavior independent of store discovery order). A plain sub-atom on an `#acc` relation is an ordinary stored-tuple match (the point row at `[m, m]`) and records `m` in `store.accConsulted`; a `*c-not` sub-atom (`not r t̄`, `#acc` only) succeeds, binding nothing, iff no row alive at `m` matches
- `runJsSub` — a `#js-def` relation inside `!(...)` (plans/v2-js-rel-in-constrain.md): mirrors `evalJsIterate` under the constraint-query substitution model — clause selection is *dynamic* (a position is `+` iff its pattern term is ground under the current substitution, per `containsSlot`; earliest declared clause ≤ the call's modes wins, as in `resolveJsModes`), `+` args are decoded for the generator, yielded rows are interned and matched against `-`-position patterns; timeless, so the component moment doesn't gate it; reuses `JS_REL_YIELD_CAP`
- active vs. existential terms — `*choose`/`*id` choice slots vs. `*var` existentials; `is` rows bind resolved values
- empty-fringe error — a seed term with no ready row (an unconstrained `?`, or one constrained only jointly with a later ask)

# pretty-ir.ts

A readable alternative to `print-ir.ts` for post-expand rules (`v2-cli --pretty`). # timeline.ts

Renders a v2 store as a timeline visualization (SVG or ASCII): moments are laid out along a time axis using a Hasse-reduced partial order, episode (`~`) tuples become labeled bars stacked in lanes, fact (`+`) tuples become lines + labels, and `is`/`constrain` rows are pulled into a sidebar. The layout pass is orientation-agnostic and is then mapped to pixels by a projector supporting horizontal and vertical orientations plus three lane-packing strategies. A horizontal-only `MomentStyle` "edges" variant (plans/v2-timeline-edge-moments.md) gives each moment its own column, but with two-tier spacing (plans/v2-timeline-fractional-columns.md): columns are ordered by (longest-path rank, token), and per-step gaps are floored to the full step (`minColWidth`) across a rank boundary but only to a small fractional width (`minFracWidth`) between same-rank — necessarily incomparable — moments, so comparable moments stay a step apart while incomparable ones cluster tightly. It draws each moment's dot on a canonical bar edge (dashed vertical ties to other bars sharing the moment), and replaces spine arrows with orthogonal dot-to-dot cover arrows (right/up/down only, routed around bars by fewest crossings then fewest turns), suppressing pairs a bar already shows as its own endpoints.

Episodes listed in `opts.collapsed` render collapsed: episodes contained in a collapsed interval `[l, r]`, and facts whose start moment lies in `[l, r)`, are dropped before ranking (so the interior moments vanish with them), and the interval is replaced by a single narrow `name...` bar (the collapsed episode's head symbol; width floored at `COLLAPSED_BAR_W` and never sized to what it hides) that keeps the collapsed episode's tuple index for source linking. Containment is judged against the uncollapsed reachability and includes the endpoints, so co-extensive episodes (`~a, ^b` puts two bars on one interval) collapse as a unit into one stand-in and expand together. The entry's `tupleIndex` names the owning episode: it decides the stand-in's label and click target, not what is hidden. Nested collapsed intervals are subsumed by their outermost container, and collapses over the same interval are one collapse. `web-v2.ts` toggles collapse by right-clicking a bar, keyed by `timelineCollapseKey` so it survives re-evaluation.

**Key terms:**
- `renderTimeline` — builds the SVG (Hasse arrows, moment dots, episode bars, fact stubs) + sidebar; used by render-output
- merged `#acc` bars (plans/v2-acc-timeline-display.md) — acc rows are never drawn one by one: `layoutTimeline` skips them (`isAccRow`) and adds one bar per `accRuns` entry of a visible relation (`opts.accOverrides`, `accRelationVisible`), carrying `Bar.acc` (`AccBarInfo`: relation, `open`, displayed `consulted` moments, moment count). Their endpoints and read moments join the displayed moment set (read moments strictly inside a collapsed interval do not resurrect it); a bar inside a collapsed interval folds away like an episode. They are packed apart from the episodes by `packAccBand`, in a band of lanes above them — most run to `top`, so in the containment forest they would adopt every later episode — one run of lanes per relation, first free lane within it, so a key's successive values read along one lane like a track. Moment dots anchor on episode edges before acc bars. Drawn square-cornered (`tl-bar-acc`, `data-tl-acc`), an `open` bar with a dashed later edge (a `stroke-dasharray` walking the rect outline), and a read marker (`tl-acc-read`) on the bar's outer corner at each consulted moment. Moment dots get a transparent hit disc with `data-tl-moment` (the inspector's click target) and `opts.selectedMoment` draws a ring
- `layoutTimeline` — orientation-agnostic layout: ranks moments by Hasse-reduced order, classifies tuples, packs lanes. A **point bar** (a tuple stored at `[m, m]`; `#acc` rows were the original source but are now merged, see above) has no extent, so the placers' non-strict "temporally disjoint" test alone would stack all the points at one moment, and the bars starting or ending there, on one lane; `isPointBar` / `barsTouch` make a point conflict with every bar it touches (`makePlacer.fits`, and a half-rank frontier in `placeBar`), and the width pass reserves the gap after a point's rank for its label, like a fact label
- `CollapsedInterval` / `opts.collapsed` — moment-token pair plus owning `tupleIndex`, drawn as one `name...` bar hiding everything the interval contains
- `Orientation` / `LaneMode` / `MomentStyle` — horizontal|vertical axis; compact|nested|tree bar-packing; spine|edges moment placement
- `momentAnchor` / `momentTies` / `orderPairs` — edges-variant layout outputs: canonical dot per moment, dashed ties, drawn cover pairs
- `renderTimelineAscii` — headless text rendering (no DOM/canvas)
- episode (`~`) bars / fact (`+`) lines — the two tuple classes laid out; `is`/`_constrain` rows go to a sidebar
- `data-source-span` — stamped (via `spanKey`) on bar rects/labels, fact labels, and sidebar rows from `store.tupleSource`, consumed by `source-link.ts`; every `Emit.span` carries columns, and span-less tuples (acc rows, engine-installed `is` rows) stamp nothing

- `Query` / `parseQuery` / `runQuery` / `QueryResult` — the query bar's text → a query (for now a bare predicate: `uses`) → titled groups of segments, each with the spans to mark (`Asserted by`, `Matched by`, `Intercepted by`, `Declared by`); the view renders groups only, so new query kinds need no view change

# rule-browser.ts

The left pane's Rules view (`RuleBrowser`, plans/v2-rule-browser.md): a query bar (with completion from the indexed predicates and back/forward history) over one column of result groups, each segment shown once, immediately, as an editable `Editor` card (syntax-highlighted, file line numbers, uses marked). Editing a card splices its text into the source textarea, the single source of truth (plain `value` assignment + an `input` event, so the source's native undo history does not cover card edits; each card has its own). Each card tracks its source range: a card's own edit shifts the cards after it; an edit in the source is diffed against the last text seen (common prefix/suffix) and shifts every range. After each parse (web-v2.ts parses on edit, without running) cards re-resolve to the segment at their start.

**Key terms:**
- `update` / `markStale` — after a good parse (rebuild index, re-render) / a failed one (keep cards, dim results); `update` leaves the cards alone while one has focus, and blur re-renders
- pinning — a pinned card stays visible whatever the query: in its result group while the query picks it, else in a `Pinned` group on top. Neither focusing nor pinning moves a card: a render whose layout (group titles, segments) is unchanged updates cards in place, so a focused card is never detached
- `relationAt` — the relation/symbol under an offset (highlighter classes `r`/`s`); Ctrl/Cmd-click in a card or in the source queries it
- `openInSource` — the card header's line link: back to the Source view with the caret there
- `state` / `restore` / `onState` — the query, its history and the pins (each by its segment's text) survive a reload: web-v2.ts keeps them in localStorage per file (`v2-rules:<file>`); restored pins resolve against the next index

# display-kit.ts

Tooltips and right-click menus for the entities of a game GUI (plans/v2-display-kit.md), handed to `-- display:` modules as `api.kit`. A display declares each visible entity with the store rows it was drawn from; the kit builds, on demand, a tooltip (label, notes, each row rendered with the line of the rule that emitted it, `store.tupleSource`; `#acc` rows have none) and a menu into the code: the emitting rule of each row (the Rules view on its relation with that card pinned), "Rules using p" per relation, "Show in timeline" (the rows' `data-tl-tuple` elements highlighted), and "Choose this" for an entity that stands for a choice. Shift+right-click keeps the browser menu. The kit only reads the store; actions go through `KitHost`, which web-v2.ts implements.

**Key terms:**
- `createDisplayKit` / `KitHost` — the page's hooks: `store`, `sourceLine`, `showRules(query, pinLine?)`, `showTuples`, `commit`
- `entity(el, spec)` / `EntitySpec` — `label`, `rows` (tuple indices or `KitRow`s), optional `choice` (a `ClickIntent`) and `notes`; a spec may be a function, evaluated on hover. Native SVG `<title>` children are dropped (ours replaces them); the innermost entity owns the menu
- `rows(store, head, M?)` / `KitRow` — a display's row reader that keeps provenance: `{ idx, head, terms (no head, no id slot), l, r }`, only rows alive at `M` when given

# default-display.ts

The bundled fallback display module (used when a program declares no `-- display:` directive). It renders an interactive icon tree from `icon T` / `icon:name` / `at X L` relations filtered to the selected choice-component's moment (`ctx.selectedIdx`), arranges each container's siblings per `left:right` / `above:below` constraints (via `icon-layout.ts`), and commits choices via `DisplayApi.commit` when an icon matches a slot of the selected component. An icon fitting several slots is handed to the host via `DisplayApi.setPending` and drawn dashed while `ctx.pending` names it. The choices strip itself (one row per component: rule names, each active term's variable name and its candidate values, slot picking for a pending term) is owned by the host page `web-v2.ts` (`renderChoices`), so every display module, bundled or `-- display:`, gets the same chooser; the old Info pane is gone and run errors render in the display area.

**Key terms:**
- `createDefaultDisplay` — factory for the fallback `DisplayModule` (used when no `-- display:` directive)
- `DisplayModule` / `DisplayApi` — the render interface and host callbacks (`peek`, `renderTerm`, `tokensEq`, `commit`, `addStyles`)
- icon tree — built from `icon` / `icon:name` / `at X L` rows alive at the selected component's moment (plain tuples, or the point rows of an `#acc at : e (@last loc)` relation)
- `ClickIntent` / `commit` — clicking an icon matching a choice slot commits `{ activeTerms, optionTuple }`; rng-labeled slots are excluded from candidate matching and singleton-row commits bind only the `you` columns (plans/v2-choice-actors.md)
- `collectConstraints` / `scopeConstraints` — read `left:right` / `above:below` rows at the moment, then keep each one only in containers where both endpoints are siblings (`ROOT_KEY` is the top-level container); the rest are counted for a warning
- `renderContainer` — one container's icons: plain wrapping row when the layout is a single cell, otherwise a `.dd-grid` with one `.dd-grid-cell` per occupied position

# icon-layout.ts

Grid packing for the default display, store-free and DOM-free so it can be tested headless. Given one container's sibling icon keys plus `left:right` / `above:below` edges, it assigns each icon a `(row, col)` by longest-path layering: column = depth in the `left:right` DAG, row = depth in the `above:below` DAG, so every surviving edge is strictly satisfied and icons pack up-and-left. The two axes are independent — a cycle drops only its own axis's edges. With no constraints everything lands in cell `(0,0)`, which the caller renders as the historical wrapping row. See plans/v2-icon-layout.md.

**Key terms:**
- `layoutIcons` — top entry: members + edges → `IconLayout` (`placements`, `rows`, `cols`, `hCycle`, `vCycle`)
- `longestPathDepths` — memoized DFS over predecessors; on a cycle reports `cycle: true` and flat depths
- `siblingEdges` — drops self-edges and edges naming non-members, so callers may pass a superset
- `isTrivialLayout` — single-cell test; the caller's signal to skip the grid entirely
